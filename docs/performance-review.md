# Performance review and agent playbook

## Scope and guardrails

This is a ranked, code-informed list of follow-up opportunities for DDS response, not a claim that the current app is slow. The application already has bounded scan queues, visible-window polling, a 100-row Overview render limit, memoized rows, cached date formatters, and main-process coalescing for identical in-flight provider requests. Do not reopen those solved areas without new profiling evidence.

The latest measured performance baseline available in this checkout is the review in [`upgrade-scan-2026-10-31.md`](upgrade-scan-2026-10-31.md), run against an earlier commit and a shared VM. It reported Recharts and its dependencies at about 358 KB of a 375 KB StockDetails chunk, and identified replacing Recharts as a proposal. Treat those bundle numbers as historical until they are reproduced against the current commit. This review's other entries are hypotheses from current code paths, not measured speedups. The renderer build could not be rerun while preparing this report because `node_modules` is absent.

**Non-negotiable:** optimize time-to-usable-work on budget hardware without changing scores, quote values, source timestamps, chart samples, error/stale states, keyboard access, or other user-visible information. Never replace unknown market data with placeholders, hide a delay, drop rows, or reduce chart fidelity to make a benchmark look faster.

Impact and effort are preliminary prioritization, not measurements. "High" means a plausible broad user benefit; each item needs the evidence in its validation column before implementation is accepted.

### First implementation candidate

The best bounded candidate to investigate first is **rank 1: a lightweight, accessible SVG stock chart**. It has the strongest existing size evidence and can reduce the StockDetails route's JavaScript work without changing the displayed price series. This is a proposal, not an implementation in this PR: its effort is medium, and equivalence must include keyboard access as well as chart appearance. Rank 2 is the lower-effort alternative if the immediate goal is to reduce work for Overview-only sessions, but it trades some first-click latency unless prefetch is tied to user intent.

## Agent and model methodology

Use this sequence for every performance change. Keep a short record of the machine, workload, measurements, and exact revision so a later agent can reproduce the decision.

1. **State a user-visible hypothesis.** Name the action that feels slow (cold start, switching desks, searching, opening a stock, or a full scan), the affected hardware class, and the suspected code path. Separate a code observation from a measured bottleneck.
2. **Establish a repeatable baseline.** Use the same app build, data fixture, display size, settings, route sequence, and network conditions before and after. Record OS, CPU model/core count, memory, GPU, power mode, Node/Electron version, and whether caches are cold or warm. On a constrained target, run repeated trials and report median and p95 rather than the fastest run.
3. **Measure the whole interaction.** Record time-to-first-usable content, click-to-result latency, UI long tasks/input delay, renderer CPU and heap, request count/concurrency, and build/chunk sizes where relevant. Include a realistic slow-machine profile; desktop-class results do not stand in for budget hardware.
4. **Change one cause at a time.** Prefer removing duplicated work, scheduling non-critical work later, bounded batching, or simpler equivalent rendering. Do not change data cadence, algorithms, quote freshness, chart samples, or visible error states as an incidental optimization.
5. **Prove equivalence and accessibility.** Add a regression that fails without the change. Compare provider fixture outputs, timestamps, scores, sorting/filtering, partial failures, retries, keyboard and screen-reader access, and screenshots where the UI changes. Preserve native parity whenever a mirrored module changes.
6. **Repeat and report honestly.** Re-run the exact baseline protocol and the repository checks. Report absolute values and percentage change for each device/workload, plus regressions and uncertainty. If the gain is below noise or shifts latency to another interaction, say so and do not claim a speedup.

### Repository-aware implementation checklist

- Read `AGENTS.md` and any matching `.agents/rules/` before touching a protected area; use `.agents/skills/verify-changes` before a code PR.
- Use deterministic fixtures for automated performance and correctness checks. Keep live provider checks separate and never use recorded/mock data as runtime data.
- For a chart or UI rewrite, preserve all source values, axes, responsive behavior, keyboard operation, names, focus states, and stale/unavailable notices; capture and compare both visual and interaction behavior.
- For market-data or scoring changes, preserve source quote time vs retrieval time, missing-vs-zero semantics, failure retention, and JS/native parity. Do not change provider cadence or default cache TTL without explicit evidence and a clear freshness treatment.
- Keep performance tests bounded and actionable: the check should fail on the regression being prevented, not on unrelated machine noise. Store benchmark output as evidence, not as a reason to weaken functional tests.
- In the PR, state the bottleneck, target workload, exact before/after numbers, fidelity/accessibility checks, and any target hardware not tested. If the environment lacks dependencies, hardware, or a display, report the limitation instead of implying verification.
